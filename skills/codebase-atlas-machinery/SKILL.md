# Codebase Atlas

Use the standard-library CLI at `scripts/atlas.py` from this skill directory. Keep the database outside the target repository.

Index a repository with `index --repo PATH --db DB`. Query a saved inventory with `query --db DB --snapshot SNAPSHOT [--graph]`. A flow JSON contains the exact `snapshot_id` and `extractor_identity`; attach it with `flow-add --db DB --snapshot SNAPSHOT --input FLOW.json`. A separate review JSON contains the assigned `overlay_id` and exact `overlay_content_hash`, plus the review decision and basis; attach it with `flow-review --db DB --snapshot SNAPSHOT --overlay OVERLAY_ID --input REVIEW.json`. Retrieve both with `flow-query --db DB --snapshot SNAPSHOT --overlay OVERLAY_ID`.

For an unclassified plain question, derive lexical terms from its wording and run `discover --db DB --repo PATH --terms TERM... --max-tokens N` before opening source files. Discover requires exactly one saved snapshot with the current extractor and an exact match to the live checkout's canonical root, HEAD/ref, structured status, and tracked-file identities. It refuses stale, old-extractor, missing, or multiple matches. It ranks source-anchored route/action candidates by exact lexical-token overlap and a deterministic tie order; it does not choose the semantic path, add synonyms, or resolve handler calls. Inspect the returned action and controller anchors, including `included_candidates` and `omitted_candidates`, then verify actor and payload details in current source. If a bounded result omits candidates, refine the lexical terms and rerun; never treat top-ranked routes as exhaustive or as semantic selection. The limit is an ASCII stdout-byte proxy, not a model-token count; complete candidates are never truncated.

After selecting a route fact from `discover`, run `evidence-pack --db DB --repo PATH --route-fact-id ID --max-tokens N` to prepare a source packet for a later flow-map worker. It repeats discover's exactly-one current-extractor and live-checkout identity selection, reads only the selected saved graph, and verifies every included source span against a safe no-follow read, saved SHA-256, UTF-8-sig decoding, and Unicode-codepoint offsets. The mandatory root contains route metadata, the complete action method, controller declaration, and saved controller route and authorization anchors when present. Candidate bundles follow saved same-method receiver invocation syntax through the saved receiver candidate and every candidate injection, exact service-type registration matches, saved implementation candidates and all declaration IDs, then methods matching the invoked member name. It explores only two invocation levels. Cross-file joins and overload matches remain candidates; `traversable: false` never becomes a bound edge. `included_candidate_bundles`, `omitted_candidate_bundles`, and `complete` expose any budget omissions. If the mandatory root cannot fit, the command withholds stdout. The byte limit is a conservative ASCII stdout proxy, not a model-token count. The packet is evidence for review and drafting, not a semantic flow conclusion.

The Luna mapping worker may prepare bounded, source-anchored flow conclusions from a complete evidence packet. Cite only a fact's exact saved `source` in the flow JSON; `controller_route_source` is auxiliary route context and cannot be cited with the route fact ID. Before creating an accepted review receipt, obtain a separate GPT-6.1 Sol High review of the assignment and the exact flow claims; bind the receipt to the reviewed overlay content hash. Code checks snapshot and overlay integrity but does not substitute for that semantic review.

Use `focus --db DB --repo PATH --snapshot SNAPSHOT --overlay OVERLAY_ID --max-tokens N` only after `flow-query` reports an accepted receipt. Focus rechecks canonical repository root, HEAD/ref, structured Git status, and each tracked path's presence, type, mode, size, and SHA-256. It does not rebuild the source graph. A stale or failed check returns no claims and a nonzero status; reindexing and reviewing a changed overlay requires a new explicit receipt.

The bundled `data/taggable-api.atlas.sqlite` contains reviewed customer-photo browsing, selfie-upload, and selection-saving maps. Their snapshot IDs and overlay IDs are recorded in the corresponding `examples/*-flow.json` and `examples/*-review.json` files. On the captured checkout, browsing fits all five conclusions in a 10,000-byte focus limit; selfie upload needs 15,000 bytes for all five; selection saving fits all six in 10,000 bytes. Check `omitted_claims` before treating any bounded response as the complete flow.

The focus limit is a conservative ASCII stdout-byte proxy that includes the final newline. It is not a model-token count and excludes prompt overhead. Claims are selected as complete units in overlay order; citations retain their complete spans and point to a deduplicated path/hash table. Complete stale diagnostics are subject to the same cap; if one cannot fit, stdout is empty and stderr reports the required byte count. The command never truncates claims, citations, or stale evidence.

Review receipts are local immutable audit records, not cryptographic signatures or provider authentication. Atlas verifies their binding to the exact snapshot, overlay hash, and extractor identity; it does not validate the truth of reviewed claims. Receiver-name invocation candidates are non-traversable syntax observations and do not establish parameter binding. Type-name candidates are not resolved graph edges. Never treat missing, rejected, stale, or mismatched review evidence as accepted.

Before returning a natural-language answer from any saved map, run `answer-check` with UTF-8 question and draft files. It calls `focus` against the live checkout and refuses unaccepted, stale, or incomplete maps. Its `semantic_review_required` packet includes the exact question and draft, every numbered claim and evidence span, and hashes binding the packet to the snapshot, extractor, overlay content, and input bytes. Send that exact packet to a separate GPT-6.1 Sol High review. The reviewer must inspect every relevant subfact within each claim against the cited spans, decide each claim's relevance to the exact question, check that relevant claims are fully covered in the draft, and identify unsupported additions. Record one ordered `claim_reviews` entry per numbered claim with `disposition: "covered"` for relevant claims whose relevant subfacts are all included, or `disposition: "not_relevant"` for claims unrelated to the question; each needs a concrete `basis`. Include `decision: "accepted"`, the exact packet SHA-256, and nonempty `reviewer_identity` and `reviewer_model` fields for audit provenance. These identity fields are labels supplied by the review record; they do not authenticate who or what produced it. A generic disposition such as `used` does not establish completeness. When a review JSON is supplied with `--review`, Atlas checks the packet hash and review shape, then prints only the exact draft bytes after acceptance; it does not judge semantic truth, relevance, coverage, or authenticate the reviewer.

In the captured selfie-upload case, an answer that said `FaceId=false`, mentioned history, and said no new rows were created was incomplete: it omitted `success=1` and `matched_count=0`, both present in focus claim 3. The separate review must reject that omission even if the draft's other statements are correct. On rejection, return the concrete missing or unsupported details to the answer worker for one correction, build a new packet, and obtain a new independent review; withhold an answer that remains rejected.
