# Codebase Atlas

Use the standard-library CLI at `scripts/atlas.py` from this skill directory. Keep the database outside the target repository.

Index a repository with `index --repo PATH --db DB`. Query a saved inventory with `query --db DB --snapshot SNAPSHOT [--graph]`. A flow JSON contains the exact `snapshot_id` and `extractor_identity`; attach it with `flow-add --db DB --snapshot SNAPSHOT --input FLOW.json`. A separate review JSON contains the assigned `overlay_id` and exact `overlay_content_hash`, plus the review decision and basis; attach it with `flow-review --db DB --snapshot SNAPSHOT --overlay OVERLAY_ID --input REVIEW.json`. Retrieve both with `flow-query --db DB --snapshot SNAPSHOT --overlay OVERLAY_ID`.

When a question supplies both the exact HTTP method and saved route literal, call `route-find --db DB --repo PATH --http-method METHOD --route LITERAL --max-tokens N` directly; no discovery pass is needed. For an unclassified plain question, derive lexical terms from its wording and run `discover --db DB --repo PATH --terms TERM... --max-tokens N` before opening source files. Discover requires exactly one saved snapshot with the current extractor and an exact match to the live checkout's canonical root, HEAD/ref, structured status, and tracked-file identities. It refuses stale, old-extractor, missing, or multiple matches. It ranks source-anchored route/action candidates by exact lexical-token overlap and a deterministic tie order; it does not choose the semantic path, add synonyms, or resolve handler calls. Inspect the returned action and controller anchors, including `included_candidates` and `omitted_candidates`, then verify actor and payload details in current source. If a bounded result omits candidates, refine the lexical terms and rerun; never treat top-ranked routes as exhaustive or as semantic selection. The limit is an ASCII stdout-byte proxy, not a model-token count; complete candidates are never truncated.

After selecting a route fact from `discover`, run `route-find --db DB --repo PATH --route-fact-id ID --max-tokens N`. If it returns one fresh reviewed map, use all returned claims. If it returns `unmapped`, run `evidence-pack --db DB --repo PATH --route-fact-id ID --max-tokens N` to prepare a source packet for a later flow-map worker. Evidence-pack repeats discover's exactly-one current-extractor and live-checkout identity selection, reads only the selected saved graph, and verifies every included source span against a safe no-follow read, saved SHA-256, UTF-8-sig decoding, and Unicode-codepoint offsets. The mandatory root contains route metadata, the complete action method, controller declaration, and saved controller route and authorization anchors when present. Candidate bundles follow saved same-method receiver invocation syntax through the saved receiver candidate and every candidate injection, exact service-type registration matches, saved implementation candidates and all declaration IDs, then methods matching the invoked member name. It explores only two invocation levels. For each first-level candidate implementation method, Atlas also scans its verified saved body for bare same-owner method calls and includes all matching overload source spans and their saved receiver-invocation facts in the same budgeted candidate bundle; these lexical candidates are not traversable, bound, or proven reachable, and are not expanded recursively. Cross-file joins and overload matches remain candidates; `traversable: false` never becomes a bound edge. `included_candidate_bundles`, `omitted_candidate_bundles`, and `complete` expose any budget omissions. If the mandatory root cannot fit, the command withholds stdout. The byte limit is a conservative ASCII stdout proxy, not a model-token count. The packet is evidence for review and drafting, not a semantic flow conclusion.

For one open route, use the staged route-map workflow. First obtain the unmapped route from `route-find`, then run `evidence-pack` and dispatch a Luna agent with its entire complete output to draft a source-supported map; the Atlas CLI does not invoke agents. Pass Luna's draft and the same route ID to `route-map-prepare --db DB --repo PATH --route-fact-id ID --draft-file LUNA_DRAFT.json --max-tokens N`. The Luna draft is a flow JSON with `overlay_schema_version: 1`, the exact current `snapshot_id` and `extractor_identity`, a title, and a nonempty `reviewed_conclusions` list. Each conclusion has a nonempty `claim` and `evidence` citations containing a fact's exact saved `source`; cite only source facts present in the complete evidence packet. `controller_route_source` is auxiliary route context and cannot be cited with the route fact ID. The selected route fact must appear in at least one conclusion. Do not infer behavior from helper names or from source bodies omitted from the packet.

For a resumable operator path, use `scripts/route_coordinator.py` with `prepare`, `draft`, `publish`, and `status`. `prepare` saves the current open-route lookup and complete evidence packet in a new run directory. Send the saved `evidence-pack.json` to Luna and save its draft outside that run directory, then run `draft --draft-file LUNA_DRAFT.json`; this preserves the exact draft and emits `review-packet.json`. Send that exact packet to a separate GPT-6.1 Sol High reviewer, save its decision JSON outside the run directory, then run `publish --review-file SOL_REVIEW.json`. The coordinator validates the independent review, publishes only an accepted result through Atlas, and checks fresh complete retrieval. It never authors map claims or reviewer decisions. `status` derives the current route state from Atlas and verifies run artifacts; the manifest's stage labels alone are not proof. Each recorded stage includes observed output bytes, elapsed time, and artifact bytes. Provider token use remains unavailable unless the provider supplies actual telemetry.

To revise one already reviewed map on the same current snapshot, pass `--revise` to `route-map-prepare`. The packet includes the exact predecessor map, accepted flow receipt, direct binding, and association review for the independent Sol review. Publish adds a new immutable map, receipt, binding, and supersession edge in one transaction; it never edits the predecessor. Route lookup, coverage, and refresh validate every saved edge and show only the current unsuperseded direct link. Exact publication retry remains idempotent after later revisions. Carried maps and routes with competing links cannot be revised; a different packet targeting a superseded predecessor is stale.

To prepare every route for one controller, use `scripts/area_coordinator.py prepare --repo PATH --db DB --anchor-route-fact-id ROUTE_FACT_ID --area-dir RUN_DIR [--max-bytes N]`. The anchor must be a unique saved `route_action`; membership is every saved route action with that exact controller type ID, and all graph fact IDs must be unique. Existing routes with one fresh accepted map count as reviewed; routes with multiple associations or stale maps fail closed. Each open route gets a deterministic child directory at `RUN_DIR/routes/<sha256-of-route-fact-id>` containing the ordinary route-coordinator run, with complete evidence tied to the area's snapshot and extractor. The area manifest freezes the selected byte budget along with the area identity; pass that exact `--max-bytes N` to every child `draft`, `publish`, and `status` command so Atlas validates the same evidence packet. Repeat `prepare` to resume missing children; a partial or corrupt child is reported and never overwritten, and all existing children are checked before new ones are created. `status` verifies the frozen area membership, current checkout, child artifact hashes, and fresh route state. As a child publishes, `status` counts it as reviewed only when that same child's accepted review and overlay match the fresh route association. `ready: true` means every route is either freshly reviewed or has a complete, identity-bound child ready for the next operator step; it does not claim cross-route proof. If a review rejects a draft, preserve that child's rejected review and start a new area run for the corrected draft; child artifacts are write-once, and a new run prepares only routes still open.

Use `impact --db DB --repo PATH --method Type.Member --max-tokens N` when a reviewed claim names a helper and its callers matter. The command selects the one current saved snapshot, returns the complete saved method definition, and scans every tracked C# file after safe reads and hash checks. It reports every exact class-qualified `Type.Member(` token pattern with a source location and a containing `Namespace.Type.Method` when the saved method spans identify one. `--method Namespace.Type.Member` is also accepted and selects by the full saved type identity, while occurrence matching uses that declaration's simple type name; both spellings return the same syntax candidates. A same-named type in another namespace may also match. This is a lexical candidate list, not compiler-resolved callers: aliases, unqualified calls, different receiver spellings, and interpolated-string expressions are excluded; overload selection and runtime binding are not resolved. The complete output is withheld when it cannot fit the ASCII stdout-byte limit. Before proposing a helper edit, include its candidate-containing methods in the change-impact answer and state any exclusions or uncertainty; check response contracts, configuration, and tests before claiming the change plan is complete.

`route-map-prepare` emits the exact independent-review packet only when the evidence is complete and fits the byte limit. Preserve that packet unchanged and send it, including its complete evidence packet and full draft claim list, to a separate GPT-6.1 Sol High review. The reviewer must assess the assignment, every numbered conclusion against its exact source spans, and the route association as separate decisions. Return a review JSON with `review_schema_version: 1`, exact `packet_sha256`, `evidence_sha256`, and `draft_sha256` copied from the packet, nonempty `reviewer_identity`, `reviewer_model: "GPT-6.1 Sol High"`, timezone-qualified `reviewed_at`, and `decision`. Include `assignment_review` and `route_association_review`, each with `decision: "accepted"` or `"rejected"` and a concrete `basis` of at least 20 characters. Include one ordered `conclusion_reviews` entry per packet conclusion, each with its `conclusion_number`, decision, and concrete basis. Set the overall decision to accepted only when the assignment, every conclusion, and the route association are accepted. Reviewer identity and model are caller-supplied audit labels; Atlas does not authenticate them.

Run `route-map-review --db DB --repo PATH --packet-file PACKET.json --review-file REVIEW.json` to recheck freshness, packet/draft hashes, exact citations, complete evidence, and all independent decisions without writing the database. A rejected review stays unpersisted. Only after it returns `result: "accepted"`, run `route-map-publish` with the same four arguments. Publish rechecks the packet against the live checkout, then writes the overlay, accepted review receipt, and route association in one SQLite transaction. It returns the `snapshot_id`, `route_fact_id`, and `overlay_id` for `route-find` and other consumers. Exact repeats are idempotent; changed evidence, drafts, or review records are refused as stale or immutable conflicts. This staged route workflow is the path for new one-route maps; do not separately run `flow-add`, `flow-review`, or `route-bind-add` for its draft.

Use `focus --db DB --repo PATH --snapshot SNAPSHOT --overlay OVERLAY_ID --max-tokens N` only after `flow-query` reports an accepted receipt. Focus rechecks canonical repository root, HEAD/ref, structured Git status, and each tracked path's presence, type, mode, size, and SHA-256. It does not rebuild the source graph. After freshness passes, it reads and hash-checks every cited source and returns each complete saved span as exact `source_snippets` text. Citations retain their fact IDs and point to one snippet and one file anchor; identical path/hash/span citations share a snippet even across fact IDs, while distinct spans stay separate. A stale or unverifiable source withholds claims; reindexing and reviewing a changed overlay requires a new explicit receipt.

Use `--max-tokens 24000`, `34000`, and `13000`, respectively, to fit each complete output. The former 10,000/15,000-byte limits are no longer current guidance and may omit conclusions; check `omitted_claims` before treating any bounded response as complete.

The focus limit is a conservative ASCII stdout-byte proxy that includes the final newline. It is not a model-token count and excludes prompt overhead. Claims are selected as complete units in overlay order together with every required exact source snippet and anchor; each trial counts the full escaped JSON response and self-reported byte count. Snippet IDs bind to the exact path, full-file hash, and complete saved span, independent of selected claims. Complete stale diagnostics are subject to the same cap; if one cannot fit, stdout is empty and stderr reports the required byte count. The command never truncates claims, citations, snippets, or stale evidence.

Review receipts are local immutable audit records, not cryptographic signatures or provider authentication. Atlas verifies their binding to the exact snapshot, overlay hash, and extractor identity; it does not validate the truth of reviewed claims. Receiver-name invocation candidates are non-traversable syntax observations and do not establish parameter binding. Type-name candidates are not resolved graph edges. Never treat missing, rejected, stale, or mismatched review evidence as accepted.

Before returning a natural-language answer from any saved map, run `answer-check` with UTF-8 question and draft files. It calls `focus` against the live checkout and refuses unaccepted, stale, or incomplete maps. Its `semantic_review_required` packet includes the exact question and draft, every numbered claim, citation, anchor, and exact cited snippet, plus hashes binding the packet to the snapshot, extractor, overlay content, and input bytes. Send that exact packet to a separate GPT-6.1 Sol High review. The reviewer must inspect every question-relevant exact detail in cited source bodies, including details omitted from map paraphrases, and check complete relevant coverage, contradictions, unsupported additions, and candidate-binding limitations. Record one ordered `claim_reviews` entry per numbered claim with `disposition: "covered"` for relevant claims whose supported question-relevant details are all included, or `disposition: "not_relevant"` for claims unrelated to the question; each needs a concrete `basis`. Include `decision: "accepted"`, the exact packet SHA-256, and nonempty `reviewer_identity` and `reviewer_model` fields for audit provenance. These identity fields are labels supplied by the review record; they do not authenticate who or what produced it. A generic disposition such as `used` does not establish completeness. When a review JSON is supplied with `--review`, Atlas checks the packet hash and review shape, then prints only the exact draft bytes after acceptance; it does not judge semantic truth, relevance, coverage, or authenticate the reviewer.

For a route discovered by `discover` or `coverage`, use `route-find --db DB --repo PATH --route-fact-id ID --max-tokens N`. You may instead select by both saved values with `--http-method METHOD --route LITERAL`. Supply exactly one selector shape: the route fact ID alone, or both the HTTP method and route literal. Exact selection compares both strings to saved `route_action` fields as written; it does not trim, change case, rewrite slashes, or substitute parameters. No exact match and multiple exact matches are errors with empty stdout, so inspect the current `coverage` output and use its unique route ID when needed. Both selector forms resolve against the same single current snapshot and then use the same route validation and rendering path.

`route-find` requires exactly one saved snapshot with the current schema and extractor that still matches the live checkout. With no accepted route association it returns `result: "unmapped"` and a structured `evidence-pack` invocation. One accepted association returns its binding and independent review receipt plus every fresh focus claim; the whole response must fit the byte limit. More than one association returns all validated association metadata as `selection_required` and never chooses one. A corrupt, dangling, stale, or changed receipt is an error rather than an unmapped result.

Use `coverage --db DB --repo PATH --max-tokens N [--offset K]` to page through every saved `route_action` fact in the one current matching snapshot. It reports global counts and each included route's method, literal, action, and association state: `open` has no reviewed link, `one_reviewed_link` has exactly one, and `selection_required` has multiple reviewed links. Continue at `next_offset` until it is `null`. For an `open` row, use the shared command template in `next_step`: run `route-find` with that row's ID, then run `evidence-pack` with the same ID when the result is `unmapped`. For `selection_required`, use `route-find` to inspect all validated associations and resolve the choice through the review process. Pages are live reads: association state can change between calls, so offsets do not freeze a cross-page snapshot and rows may shift if the saved checkout or database changes. The command claims coverage only of saved route facts in that selected snapshot, not all routes in the codebase or runtime behavior. Its limit is ASCII stdout bytes including newline, not model tokens; rows are complete and never truncated, and stdout is withheld when the required page cannot fit.

Attach a route association with `route-bind-add --db DB --snapshot SNAPSHOT --input BINDING.json`. The input has `binding` and `association_review` objects. The binding includes `binding_schema_version: 1` and names `snapshot_id`, `extractor_identity`, `route_fact_id`, `overlay_id`, and the exact accepted flow `flow_review_receipt_hash`. Its canonical SHA-256 is computed by Atlas; put that value in the association review's `binding_hash`. The review also repeats all five binding identifiers and includes `review_schema_version: 1`, `decision: "accepted"`, nonempty `reviewer_identity`, `reviewer_model`, timezone-qualified `reviewed_at`, and a concrete `review_basis`. Atlas computes a separate association-review hash. Both records are immutable; an exact repeat is idempotent and a conflicting repeat is refused. Only the route action, exact same-snapshot overlay, and exact accepted flow receipt can be bound. A route citation or matching flow title is not an association.

For the one-route refresh pilot, run `route-refresh --db DB --repo PATH --from-snapshot SNAPSHOT --route-fact-id ID --max-tokens N` on the changed checkout. It requires exactly one accepted source association and captures a current snapshot from the same canonical root, current schema, and extractor. Atlas builds complete origin and target evidence packets and carries the association only when their canonical contents match after excluding `snapshot_id` and budget fields, the route and cited facts are unique and unchanged, and every citation source still verifies against its full-file hash and span. The immutable carry record stores the original snapshot, overlay, receipt, binding, association-review hashes, and packet digest in the same transaction that saves the target snapshot. A failed check or transaction leaves no carry. This pilot refuses to chain a carry from another carried source. It does not create a new semantic review; retrieval exposes the original reviewer identity, date, hashes, and carry provenance. It preserves the extractor's lexical and two-invocation-level limits.

To calculate the binding hash for the review receipt, canonicalize only the `binding` object as JSON with ASCII escaping enabled, sorted keys, and separators `(',', ':')`, then SHA-256 the resulting ASCII bytes. In Python this is `hashlib.sha256(json.dumps(binding, ensure_ascii=True, sort_keys=True, separators=(',', ':')).encode('ascii')).hexdigest()`. Do not add `binding_hash` or `association_review_hash` to the binding object; Atlas computes and checks both hashes. The `route-bind-add --snapshot` value must equal `binding.snapshot_id`.

In the captured selfie-upload case, an answer that said `FaceId=false`, mentioned history, and said no new rows were created was incomplete: it omitted `success=1` and `matched_count=0`, both present in focus claim 3. The separate review must reject that omission even if the draft's other statements are correct. On rejection, return the concrete missing or unsupported details to the answer worker for one correction, build a new packet, and obtain a new independent review; withhold an answer that remains rejected.
