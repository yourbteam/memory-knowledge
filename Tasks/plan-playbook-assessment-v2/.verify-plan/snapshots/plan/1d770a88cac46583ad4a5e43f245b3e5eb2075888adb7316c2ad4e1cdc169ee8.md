# Plan Playbook V2 Implementation Plan

## 1. Goal and Terminal Outcome

Replace the current prose-only `plan-playbook` with a controller-backed planning harness that:

- enters planning only from sufficient grounded evidence;
- produces a decision-complete implementation plan with exact implementation and verification anchors;
- runs an obligation-complete `verify-plan` stage followed by three independent, Plan-V2-owned internal-readiness, requirements-coverage, and requirements-satisfaction lenses in a fixed order;
- invalidates every prior stage result after any plan edit;
- distinguishes ordinary approval from already-authorized convergence execution;
- proves practical value through fresh downstream implementers that receive the recorded plan/package and only the bounded source roots the real workflow requires;
- promotes transactionally into the canonical managed skill without leaving the candidate alias installed.

Implementation is complete only when all seven canonical acceptance criteria in section 12 pass, the candidate evaluation passes, canonical promotion verifies, and a fresh invocation selects the upgraded `plan-playbook`.

## 2. Scope

### In scope

- An isolated `plan-playbook-v2` candidate skill.
- A deterministic plan-package and lifecycle controller.
- One canonical shared tree-digest helper used by every planning, convergence, evaluation, installation, and promotion consumer.
- Exact planning artifact, hardening, approval, and terminal contracts.
- Independent subagent lifecycle and shared budgets.
- Integration corrections in `task-workflow` and `playbook-convergence-loop`.
- Deterministic controller, contract, evaluator, installer, and promotion tests.
- A backward-compatible runtime-ID uniqueness correction in the shared agent-slot helper and its focused tests.
- Fresh-agent practical evaluation using the approved E10-E14 source artifacts.
- Transactional source and installed-skill promotion with rollback.

### Out of scope

- Changes to `working-agreement/DIRECTIVES.md`.
- Rewriting `doc-gap-closure-loop`, `requirements-coverage-gap-loop`, or `requirements-satisfaction-gap-loop`. Their current contracts are migration evidence for the V2-owned lenses, not runtime dependencies.
- Further changes to `verify-plan` beyond the separately proven obligation-ledger correction recorded in `verify-plan-coverage-remediation-plan.md`.
- Implementing a generic workflow engine outside the planning domain.
- Remote deployment, database work, secret access, or external messages.
- Committing or pushing changes without separate repository-scoped approval.

## 4. Locked Architecture

### 4.1 Candidate-first development

Create `skills/plan-playbook-v2/` as an explicit-only managed candidate. Do not change canonical `skills/plan-playbook/` during candidate construction or evaluation.

The candidate tree is:

```text

  agents/openai.yaml
  references/entry-and-evidence.md
  references/plan-package.md
  references/hardening-lifecycle.md

  references/evaluation.md

  integration/task-workflow.SKILL.md

```

`agents/openai.yaml` must use `$plan-playbook-v2` as its default prompt and set `allow_implicit_invocation: false`. Candidate evaluation must not alter ordinary canonical routing.

### 4.2 Parent and agent ownership

The parent orchestrator is the only writer of plan text, state, ledgers, audit artifacts, and findings dispositions.

Delegated roles are assessment-only:

- `VERIFY_PLAN_VERIFIER`
- `VERIFY_PLAN_CRITIC`
- `INTERNAL_READINESS`
- `REQUIREMENTS_COVERAGE`
- `REQUIREMENTS_SATISFACTION`

Each role receives the frozen objective, requirements, current plan, plan hash, evidence index, implementation-surface map, and authoritative roots. It does not receive producer rationale, hidden expected answers, a proposed fix, or a sibling role's conclusions. Only `VERIFY_PLAN_CRITIC` receives the controller-owned validated raw-finding and obligation-assessment snapshots from its paired verifier because independent adjudication of those exact records is its authoritative contract; it still receives no verifier rationale or hidden fix.

The candidate owns one immutable `PLAN_PLAYBOOK_V2_HARDENING_LENSES_V1` contract in `references/hardening-lenses.md`. The controller hashes its raw bytes at initialization and binds that identity to every later-lens input, output, stage result, package, replay, evaluation, and promotion check. Its three exact lenses are:

- `INTERNAL_READINESS`: the plan is grounded in the frozen evidence, internally consistent, decision-complete, and implementable by a competent engineer without rediscovery or unstated choices.
- `REQUIREMENTS_COVERAGE`: every explicit, implied, negative, and nonfunctional requirement is either fully addressed by plan obligations and implementation/verification anchors or explicitly excluded by the frozen charter.
- `REQUIREMENTS_SATISFACTION`: every addressed requirement would actually hold end-to-end once implemented against the real code, runtime, data, integration boundaries, and already-shipped sibling behavior.

Each lens runs in its own fresh subagent against the same frozen plan, requirements, evidence, source snapshots, and lens-contract hash. A PASS from one lens cannot satisfy another. The current standalone hardening skills are design provenance only and are not imported, invoked, or consulted by Plan V2 at runtime.

Every role must have a unique runtime agent ID, input-envelope hash, output hash, attempt number, completion evidence, close evidence, and released slot. Parent-level spawn, wait, and close capability is mandatory. Absence returns `BLOCKED`; roles are never collapsed into the parent.

### 4.3 Controller boundary

Implement `skills/plan-playbook-v2/scripts/plan_package.py` as the authority for planning state and terminal validity. It may use standard-library modules and the existing shared stage-result and verification-ledger contracts. It must not write outside paths explicitly supplied by the caller.

The controller owns:

- canonical JSON hashing and file-byte hashing;
- immutable charter and requirement freeze;
- entry-mode validation;
- profile and budget selection;
- draft and revision plan hashes;
- role attempts and slot-close evidence;
- ordered stage-result recording;
- findings and disposition state;
- full-stage invalidation after a revision;
- terminal package emission and hash validation.

The controller does not spawn agents or decide planning content.

At `init`, the controller also reads the candidate-owned `references/hardening-lenses.md`, requires the exact contract ID and all three role sections, hashes its raw bytes, publishes and fsyncs the content-addressed run snapshot, reopens it, and only then stores the lens fields in state. Every later role preparation, stage record, package operation, replay, evaluation, and promotion reopens those bytes and rejects candidate-source drift or snapshot tamper. A candidate source edit can affect only a new controller run; it cannot reinterpret an existing run.

For a successful VERIFY_PLAN critic assessment, terminal-envelope actionability is derived from dispositions and obligation approvals together: `new_gaps` contains exactly the canonical verifier findings decided `FIX NOW|IMPLEMENT LATER`, `open_gap_ids` is their sorted ID set, and `ACKNOWLEDGE|DISMISS` findings appear only in the immutable report and findings ledger. `closed_gap_ids` contains only prior controller gap IDs closed by explicit transitions and never a newly dismissed finding ID. The envelope verdict is `GAPS` when that actionable set is non-empty or an assigned assessment is critic-approved GAP, `BLOCKED` when an assigned assessment is critic-approved BLOCKED, and otherwise `PASS` only when every assigned obligation is critic-approved SUPPORTED. The controller rejects a critic envelope whose verdict, gap/blocker arrays, assignment, or approvals disagree. Runtime inability to complete the critic is recorded through the controller attempt/blocker path, not a fabricated successful critic output.

The same derivation applies to each successful later single-assessor output using its own findings and dispositions: only `FIX NOW|IMPLEMENT LATER` become `new_gaps` and open IDs, `GAPS` means that set is non-empty, and `PASS` means it is empty. Assessor-produced `BLOCKED` for an incomplete assessment has empty findings/dispositions and must carry a valid canonical blocker; CAP_REACHED is controller-derived. This keeps later-gate findings on the same `OPEN -> APPLIED` revision path without adding another critic role.

For INLINE, no artifact path is materialized: `record-stage` requires `--source-attempt-id`, forbids `--artifact`, reopens the controller-owned successful output snapshot, revalidates `artifact_transfer.form=INLINE`, content, and hash, and stores those exact Markdown bytes in the gate result. For FILE, `materialize-artifact` is the only writer: it requires `--task-directory` to equal frozen `task_root`, revalidates the successful attempt and transfer hash, writes those exact bytes atomically to the stage's fixed task-root-relative target, re-reads the file, and records the resulting path/hash; the later `record-stage` call requires both the same `--source-attempt-id` and `--artifact` equal to that controller-recorded materialized path. It rejects a missing or extra artifact argument, different target, changed content, parent rewrite, symlink, or out-of-root path. The parent never reconstructs assessor prose. INTERNAL_READINESS, REQUIREMENTS_COVERAGE, and REQUIREMENTS_SATISFACTION consume only the named successful attempt snapshot through this INLINE/FILE matrix. VERIFY_PLAN forbids `--source-attempt-id` and requires `--artifact` equal to the controller-rendered summary: the controller derives the aggregate terminal envelope from the validated verification ledger, critic dispositions, blocker state, and same-hash attempts after `render-verify-summary`. No stage accepts a caller-authored envelope or digest.

`record-findings` validates the named successful attempt outputs and derives findings and dispositions directly from their controller-owned snapshots. VERIFY_PLAN requires one verifier output and its paired critic output. It reopens the critic input envelope, requires its raw-findings bytes to equal the verifier snapshot, requires the critic output findings to be byte-identical, and requires exactly one fingerprint-bound disposition per finding. For a genuinely new finding it persists those verifier bytes plus the critic's decision and required new-finding classification once. For a carried ID/fingerprint it requires null new-finding classification and preserves the original first-seen finding and provenance bytes; a changed fingerprint under an existing ID or a supposedly carried unknown identity fails closed. Other stages require one primary output, no critic output, and exactly one primary-assessor fingerprint-bound disposition per finding. For each finding in one accepted assessment, the controller derives `assessment_sequence=1` when no disposition exists or exactly the prior maximum plus one, then enriches the persisted disposition with that sequence, the output role/stage, round, verification iteration, assessed plan, and revision. Exact replay identifies the already-recorded attempt/output and returns the same occurrence without incrementing; a different attempt cannot reuse a sequence. Actionable dispositions have immutable assessment-time `status=OPEN`; non-actionable dispositions have `status=NO_ACTION`. `record-revision` never mutates a disposition: for each named latest OPEN disposition it appends the exact `OPEN -> APPLIED` finding transition below referencing that disposition's assessment sequence. Caller-authored disposition or transition files are never accepted.

`record-verification-ledger` is the only same-revision ledger update. It is legal only while `status=HARDENING`, the active stage is VERIFY_PLAN, and the plan/evidence/surface/decision hashes are unchanged. It runs the shared obligation-aware ledger validator, requires the next monotonic iteration, and preserves every prior inventory, assignment, assessment, critic snapshot identity, finding, and iteration record byte-for-byte. For the new iteration it derives an exact expected record from the paired controller-owned verifier and critic snapshots: active plan/evidence/inventory hashes, assigned coverage and obligation IDs, every verifier assessment and assessment fingerprint, exact critic approvals and snapshot references, verifier finding count, disposition/provenance counts, and every finding identity/current status/action. The candidate ledger must append exactly that assignment and its complete one-to-one assessment/approval set plus exactly the new finding records; omitted, additional, duplicate, foreign-binding, or coarse-coverage-only records are rejected. An iteration-2+ identity absent from the input ledger requires one non-null provenance value; a carried identity requires null provenance and a new controller-derived assessment-sequence disposition occurrence. The controller derives coverage `checked|fixed` state from current approved obligation history, independently runs `next-assignment`, and requires `--can-stop` to agree with zero remaining obligations and zero GAP/BLOCKED states. A later finding that names a supported obligation resets it and its owning coverage item before another assignment. It snapshots the accepted bytes before atomically replacing `verification_ledger_sha256` and does not invalidate successful pairs on the same plan hash. `record-revision` remains the only command that may bind a changed plan or evidence artifact; it builds a new content-bound inventory, selectively carries only byte-identical obligation bindings, invalidates all changed bindings and stage satisfaction, and preserves immutable verification history and the next global iteration.

Every verify-plan verifier and critic returns its complete per-attempt Markdown report unchanged through `artifact_transfer`, and successful finalization retains the raw role-output path/hash. After every critic-complete iteration termination, whether `PASS`, `GAPS`, `BLOCKED`, or `CAP_REACHED`, `render-verify-summary` deterministically renders the exact required summary headings and tables from the validated ledger, dispositions, attempt provenance, and the ordered controller-owned role reports. It copies report text only into clearly attributed iteration appendices and never rewrites assessor prose. `record-stage` requires and re-hashes this summary through `--artifact`; no verify-plan terminal result can be recorded without it. The controller-owned summary is the single VERIFY_PLAN stage artifact. No individual role is treated as the producer of aggregate totals it could not observe.

The embedded internal terminal envelope uses exactly the shared top-level stage-result field set from `skills/_shared/STAGE_RESULT_CONTRACT.md`: `stage`, `iteration`, `attempt`, `assigned_requirement_ids`, `assigned_gap_ids`, `owned_blocker_ids`, `verdict`, `open_gap_ids`, `closed_gap_ids`, `new_gaps`, `new_blockers`, `record_transitions`, `evidence`, and `artifact_paths`. It is not directly consumable by `convergence_state.py`. Planning stage values are exactly `plan-verify`, `plan-internal-readiness`, `plan-requirements-coverage`, and `plan-requirements-satisfaction`. Internal `new_gaps` uses the exact finding schema in section 5.5. Every internal `new_blockers` item contains exactly `id`, `type`, `practical_impact`, `evidence`, and `required_resolution`, with `type=EVIDENCE|RUNTIME|APPROVAL`. Every transition contains exactly `kind`, `id`, `from_status`, `to_status`, and non-empty `evidence`.

`record-stage` binds `stage`, outer `iteration`, attempt, canonical assigned requirement IDs, gap/blocker IDs, transitions, verdict, and artifact paths to controller state and the recorded role attempts. It validates the shared PASS/GAPS/BLOCKED/CAP_REACHED semantics, requires all evidence entries to be non-empty path/line or command-result strings, rejects unknown fields and foreign IDs, then computes `terminal_envelope_sha256` from the assessor-owned snapshot or controller-derived verify-plan aggregate. No terminal-envelope field is accepted from the parent or trusted without derivation or state comparison.

`stage-result` is a separate aggregate adapter for `convergence_state.py`; it never forwards an internal gate envelope. It loads the active convergence state and requires either status `plan` or status `blocked` with `blocked_from_status=plan` and `blocked_stage=plan`. It binds `iteration` to `outer_iteration`, computes the next `plan` stage attempt from existing convergence stage records, and derives sorted `assigned_requirement_ids` from the active convergence state's requirement keys. Those IDs must exactly equal the plan package requirement IDs; the adapter contains no task-specific identifier literals.

The aggregate output uses exactly the live `convergence_state.py record-stage` nested schemas:

- `stage` is `plan`.
- Every `new_gaps` item contains exactly `id`, `requirement_ids`, `source_stage`, `impact`, `evidence`, `status`; source stage is `plan`, status is `open`, impact comes from practical consequence, and evidence is the canonical joined evidence records.
- Every `new_blockers` item contains exactly `id`, `stage`, `status`, `type`, `reason`, and `required_evidence`; stage is `plan`, status is `open`, and internal `EVIDENCE|RUNTIME|APPROVAL` maps to `external|execution|approval`.
- Direct `PASS` from outer `plan` requires an emitted PASS package and lists its manifest in `artifact_paths`. When inner planning has passed but outer state is blocked from plan, the adapter advances every mapped nonterminal plan blocker by exactly one live edge per successive attempt: `open -> fixed-awaiting-verification` with the controller resolution/bundle receipt as evidence, then `fixed-awaiting-verification -> verified` with the emitted package's canonical `validate-package` result as evidence, then `verified -> closed` with the same validated manifest and final-plan hash as evidence. The first two successor attempts remain `BLOCKED`; only the closing attempt is `PASS`, lists the manifest, and selects the lexicographically first closed mapped blocker as the deterministic resume anchor. Already terminal mapped blockers remain unchanged. `GAPS`, ordinary `BLOCKED`, and `CAP_REACHED` are derived from controller state and use mapped open records without a package.
- Every adapter call also reconciles all outer gaps owned by stage `plan` from each finding's derived latest status, never from the existence of any historical transition. Current status OPEN places the ID only in `open_gap_ids`; when persisted outer status is `closed|non-gap`, it first emits one evidence-bearing `closed|non-gap -> open` transition bound to the later assessment sequence, finding fingerprint, assessor-output hash, and assessed plan hash. The shared gap lifecycle clears terminal-only closure metadata on that reopen. Current status APPLIED places an existing effective outer open ID only in `closed_gap_ids` and emits exactly one outer `gap` transition `open -> closed`; its evidence joins the latest disposition sequence and fingerprint, matching controller transition, revision receipt, corrected plan hash, and, on final PASS, the validated package manifest. Current status NO_ACTION places an existing effective outer open ID only in `closed_gap_ids` and emits `open -> non-gap` with evidence binding the latest assessor output hash, disposition sequence, decision, and rationale. The adapter and live consumer derive each gap's effective persisted status after applying the ordered transitions, then require every `open_gap_ids` and `closed_gap_ids` member to match that effective status; an ID can never appear in both sets. An outer plan-owned gap without one of these exact current-state derivations fails closed; the adapter never infers status from an older APPLIED occurrence. This mapping runs for revised GAPS as well as PASS, so one attempt may reopen, close, or mark non-gap prior IDs and open newly actionable IDs while still reconciling the complete owned set required by the live consumer.
- Assigned/open/closed gap and blocker IDs, transitions, evidence, and artifact paths are derived from controller and convergence state, never caller prose.

Before writing each result file, the adapter invokes the live `convergence_state.py cmd_stage` path against a temporary copy of the current convergence state and discards that copy after validation. The result file is therefore the only input the consumer passes to the real `record-stage`; no separately asserted artifact ID is permitted. After each outer lifecycle BLOCKED successor is recorded, the consumer re-runs the adapter against the newly persisted blocker status until it emits the final PASS. Attempt numbers remain live-derived and strictly increase. A retry at any point derives the same next edge from current state, while a repeated recorded attempt is accepted only by live idempotency. Temporary-root tests pass direct and three-successor resumed PASS plus GAPS, BLOCKED, and CAP_REACHED through the real `record-stage` path; execute both `closed -> open` and `non-gap -> open` through real `cmd_stage`; reopen and re-read the final stored gap state; prove terminal metadata clearing and exact replay; and reject skipped/reordered edges, malformed nested records, arbitrary requirement substitution, unknown artifact IDs, effective-status mismatch, and outer-attempt drift.

Temporary-root convergence tests additionally prove `GAPS -> record-revision -> PASS` closes every prior outer plan gap with evidence before implementation transition, revised GAPS can close applied IDs while opening new IDs, a later OPEN occurrence reopens an older APPLIED or NO_ACTION outer gap before reporting it open, and a latest NO_ACTION occurrence maps an existing effective open gap to one evidence-bearing `non-gap` transition. They reject overlap between open/closed IDs, omitted, invented, stale-history-derived, unmatched, evidence-free, or persisted-status-inconsistent gap transitions.

The JSON above is the exact attempt-array element schema, and each `evidence` item is exactly one member of this discriminated union:

`dispositions.json` contains `schema_version`, `plan_sha256`, `dispositions`, and `finding_transitions`. Every persisted disposition contains exactly `finding_id`, `finding_fingerprint`, `assessment_sequence`, `stage`, `round`, `verification_iteration`, `decision`, `rationale`, `parent_action`, `new_finding_classification`, `status`, `assessed_plan_sha256`, and `assessed_revision`. `record-findings` derives the positive per-finding assessment sequence, canonical stage, round, positive role-local verification iteration, and two assessment fields from the frozen attempt/output/finding identity; role output may not supply the enriched fields. `decision` is exactly the live spaced value `FIX NOW|IMPLEMENT LATER|ACKNOWLEDGE|DISMISS`; underscore aliases are rejected. `new_finding_classification` is null for verify-plan iteration 1, null for an iteration-2+ carried ID/fingerprint already present in the input ledger, and exactly `MISSED IN FIRST PASS|INTRODUCED BY FIX|NEWLY REVEALED|COVERAGE QUEUE|SCOPE DRIFT` for a genuinely new iteration-2+ identity; it is null for non-verify stages. Immutable assessment-time `status` is `OPEN|NO_ACTION`: both `FIX NOW` and `IMPLEMENT LATER` require `OPEN`, while only `ACKNOWLEDGE` and `DISMISS` require `NO_ACTION`.

Every `finding_transitions` item contains exactly `{finding_id,finding_fingerprint,sequence,disposition_sequence,from_status,to_status,applied_revision,applied_plan_sha256,revision_receipt_sha256}`. Both sequence values are positive; `sequence` is contiguous per finding and `disposition_sequence` identifies one exact immutable disposition occurrence. The sole legal transition is `OPEN -> APPLIED`; it references that finding's latest current disposition occurrence, which must be OPEN, plus the successor revision/plan and exact revision receipt created by the same `record-revision` transaction. A finding's current status is derived exclusively from its greatest `assessment_sequence`: it is `NO_ACTION` when that latest disposition is NO_ACTION; otherwise it is `APPLIED` only when that exact latest OPEN occurrence has one matching transition, and `OPEN` when it has none. An older APPLIED occurrence never overrides a later OPEN or NO_ACTION occurrence. A transition for an unknown/fingerprint-mismatched disposition, duplicate transition sequence or disposition reference, non-latest OPEN disposition, foreign revision/hash/receipt, or any status reversal fails closed. Role output, controller state, verification ledger current-status projection, rendered summary, emitted package, and tests preserve critic-authoritative VERIFY_PLAN bytes, single-assessor-authoritative later-stage bytes, and the immutable disposition/transition history end-to-end. There is exactly one disposition per `(finding_id,assessment_sequence)`, no orphan disposition or transition, and exactly one finding record per ID. Package and ledger replay reopen the content-addressed plan snapshot named by each `assessed_plan_sha256`, require its revision to equal `assessed_revision`, validate every applied successor receipt, and reject history relabeled to the package's final plan hash.

The emitted package `findings.json` contains exactly `schema_version`, `plan_sha256`, `revision_history`, `findings`, `dispositions`, and `finding_transitions`, preserving validated records and every original assessment identity. `revision_history` contains one ordered record per controller revision, each exactly `{receipt,receipt_sha256,plan_markdown}`; `receipt` has the exact controller receipt fields above, `receipt_sha256` hashes its canonical bytes, and `plan_markdown` hashes to `receipt.plan_sha256`. Emission reopens every controller receipt and snapshot to construct these self-contained records, validates the predecessor chain, and rejects omission, reordering, changed bytes, a current OPEN actionable finding, or an actionable finding without an immutable disposition/current-status derivation. ### 5.8 Hardening order and invalidation

Across one complete planning-controller run:

1. Validate the latest draft, surface map, and obligation-aware verification ledger against the frozen plan/evidence identities.
2. Build a finite content-bound obligation inventory. When it has never been reviewed and there is no assignment history, permit one deterministic bootstrap assignment; no obligation counts as supported yet.
3. Run one verifier and one critic on that same bootstrap assignment and plan hash. The verifier returns exactly one `SUPPORTED|GAP|BLOCKED` assessment per assigned obligation; the critic approves or rejects inventory completeness, each assessment, and every finding disposition in one exact snapshot. A rejection requires a rebuilt inventory; an omitted decision, unfinished assignment, or second pre-approval assignment fails closed. Iteration 1 exists only for the initial draft; a revised plan uses the next globally monotonic number and a successor inventory.
4. Continue bounded assignments until `next-assignment` returns an empty list. A later finding that touches a supported obligation resets it before scheduling; a changed section, evidence, or dependency binding selectively invalidates its assessment. Store every pair and exact critic snapshot in order; only critic-approved actionable findings can drive edits.
5. Require verification-ledger `check --can-stop`: the active inventory is approved, every non-excluded current obligation is critic-approved SUPPORTED, zero GAP/BLOCKED obligations remain, and zero actionable findings remain. Coarse coverage status cannot satisfy this gate. Only then record terminal `VERIFY_PLAN=PASS`.
6. Run a fresh `INTERNAL_READINESS` subagent with the state-bound `PLAN_PLAYBOOK_V2_HARDENING_LENSES_V1` snapshot and require its result.
7. Run a different fresh `REQUIREMENTS_COVERAGE` subagent under the same lens-contract and plan hashes only after internal readiness `PASS`.
8. Run a different fresh `REQUIREMENTS_SATISFACTION` subagent under those same hashes only after coverage `PASS`.
9. Emit only after all four stages report `PASS` on the same plan hash, the three later stages bind the same owned lens-contract hash, and every slot is closed.

The verify-plan same-hash subloop is bounded by the shared attempt budget while reserving one attempt for each of the three later gates: at most three successful pairs for LIGHT and ten for SUBSTANTIAL before continuation, fewer after retries. The approved continuation adds exactly ten more possible verifier/critic pairs while preserving the three later-stage reservations. Across changed hashes, `verification_iteration` remains globally monotonic and the active `verify_plan_iteration_limit` applies to the complete run; revision never replenishes it. Exhaustion with actionable findings, unsupported obligations, or an unapproved inventory returns `CAP_REACHED`, never PASS.

`GAPS` returns to the parent. The parent records accepted dispositions, calls `prepare-revision`, edits only the five files in that deterministic workspace, and calls `record-revision --proposal` with every accepted finding ID. The same two-command path is legal from `EMITTED` only for a material implementation-time change and then performs the section-5.7 invalidation-marker protocol before returning to `DRAFTED`; the currently emitted root package remains byte-identical until successor emission. In either state `record-revision` recomputes the complete revision basis, appends one exact OPEN-to-APPLIED transition for each named finding's latest current OPEN disposition occurrence and binds that occurrence's `assessment_sequence` as `disposition_sequence`, preserves all prior iteration/finding/disposition/transition history, resets affected coverage items to unchecked, invalidates every prior stage PASS and every later-gate attempt/result, and retains consumed attempts, elapsed time, and the next global verification iteration. The next action must be that next numbered verify-plan iteration on the new hash. Prior same-hash successful pairs remain historical evidence but cannot satisfy the revised hash's PASS.

`BLOCKED` names missing evidence, approval, runtime, or research return. `CAP_REACHED` names the exact cap. Neither may emit a PASS package.

Every case has exactly `case_id`, `case_class`, `source_refs`, `visible_inputs`, `implementation_sources`, `public_contract`, `controller_inputs`, `hidden_gold`, and `research_resume_package`. `case_class` is `SMALL_GROUNDED|SUBSTANTIAL_MULTISURFACE|EVIDENCE_UNCERTAIN`. Every file reference has exactly `path` and `sha256`; source references additionally have `evidence_id`. `controller_inputs` has exactly `entry_mode`, `charter`, `direct_requirements`, and `direct_evidence_index`. `charter` is always a non-null answer-free file reference. SMALL_GROUNDED and SUBSTANTIAL_MULTISURFACE use DIRECT with both direct references non-null; EVIDENCE_UNCERTAIN uses RESEARCH_PACKAGE with both direct references null and no initial package. `implementation_sources` is a non-empty, case-neutral list of repository roots or source snapshots the implementer would receive in the practical workflow, each with exactly `repository_key`, `path`, and `tree_sha256`. `research_resume_package` is null except for the evidence-uncertain case, where it has exactly `path` and `tree_sha256`. `prepare` recomputes every controller-input hash, runs the controller's mode-specific read-only schema validators over those exact bytes, and rejects wrong-mode nullability, a missing required input, or any path/hash overlap among controller inputs, visible/public inputs, implementation sources, evaluator code, and hidden gold. It then applies the shared `ASSESSMENT_SOURCE_SNAPSHOT_V1` producer to every implementation source, stores the resulting immutable run-owned records in prepared-run, and stages only those snapshot paths to implementer agents; source mutation during copy or later snapshot tamper fails. `source_bundle_sha256` is computed only after every `source_refs` path strict-resolves inside the fixture source root and its raw-file SHA-256 equals the asserted value. The evaluator then forms one exact record `{case_id,evidence_id,path,sha256}` per source reference, with `path` normalized to fixture-root-relative UTF-8 POSIX form; rejects an unknown case, an absolute/traversing/symlink path, duplicate `evidence_id` or duplicate path within a case, and any duplicate full record; sorts records by the UTF-8 byte tuple `(case_id,evidence_id,path,sha256)`; serializes the array as UTF-8 canonical JSON with recursively sorted keys, separators `,` and `:`, ASCII escaping enabled, and no trailing newline; and hashes those exact bytes. Fixture preparation, prepared-run reopen, and scoring all rederive that digest from source bytes rather than trusting the manifest field. The four authority fields name the fixture-root-relative immutable files and their raw-byte hashes. Every case request, visible input, implementation source, public canonical ID/boundary statement, hidden critical set, forbidden claim, and expected transition must be generated as an exact projection of the corresponding reviewed authority case; fixture-local authored substitutes are forbidden. Preparation revalidates the authority and review before reading any case and requires the manifest's complete three-case projection to be one-to-one and byte-equal.

Evaluator implementation-source snapshot records use the exact shared seven-field authoritative-root record and are nested in each matrix row's prepared implementer input; they are therefore covered by the existing matrix/input-envelope hashes rather than a new top-level prepared-run field. Every materializer, record transaction, scorer, and promotion validator reopens those nested manifests and snapshot trees. No implementer receives the mutable fixture-declared source path.

The planner public-contract file has exactly `schema_version`, `case_id`, `requirement_ids`, `obligation_ids`, `negative_boundaries`, and `planner_output_schema`. `negative_boundaries` contains exact `boundary_id` and neutral `statement` fields describing constraints visible in the source requirement, never a selected implementation or expected pass/fail answer. IDs are unique canonical IDs. `planner_output_schema` is exactly `LEGACY_PLANNER_V1|V2_PLANNER_V1` as applicable. This file is planner-visible only and is forbidden from implementer staging.

The implementer output contract is one case-neutral JSON Schema file owned by the evaluator and contains only the generic `IMPLEMENTER_V1` field names, types, nullability, and enums from section 8.4. It contains no case ID, expected requirement/obligation/boundary ID, boundary statement, expected transition, critical set, forbidden claim, source path, or scoring threshold. Implementers must derive every returned requirement and obligation identifier from the recorded plan/package; hidden gold alone owns expected scoring sets.

The hidden-gold file has exactly `schema_version`, `case_id`, `critical_requirement_ids`, `critical_obligation_ids`, `required_negative_boundary_ids`, `forbidden_scope_claims`, `forbidden_evidence_claims`, and `expected_transitions`. Forbidden-claim records contain exactly `id`, `claim`, and `evidence_ids`. `expected_transitions` has exactly `legacy` and `v2`; each is a non-empty ordered array of `{phase, terminal_verdict, blocker_code}` records. It contains no prose plan, implementation steps, or agent prompt. `prepare` requires non-empty critical requirement, obligation, and negative-boundary sets and verifies they are subsets of the public canonical IDs; therefore no metric has a zero denominator.

The managed snapshot has exactly `schema_version`, `manifest_sha256`, `installed_root`, `backup_root`, `skills`, and `recorded_at_utc`. Every skill record has exactly `name`, `installed_state`, `tree_sha256`, and `backup_relpath`; absent skills use `installed_state=ABSENT` and null hashes/paths. Present skills use `PRESENT`, a tree hash, and a content-addressed backup directory beneath `backup_root`. `snapshot-managed` copies and re-hashes those bytes before writing the snapshot. `restore-managed` rejects changed snapshot or backup hashes, restores presence/absence exactly, and re-hashes the restored tree.

The prepared-run state has exactly `schema_version`, `run_root`, `fixture_root`, `fixture_tree_sha256`, `fixture_manifest_sha256`, `fixture_authority_path`, `fixture_authority_sha256`, `authority_review_path`, `authority_review_sha256`, `legacy_tree_sha256`, `candidate_tree_sha256`, `implementer_schema_sha256`, `candidate_check_requests`, `candidate_check_attempts`, `candidate_check_evidence_path`, `candidate_check_evidence_sha256`, `matrix`, `outer_attempts`, and `created_at_utc`. `candidate_check_requests` has exactly `explicit_path`, `explicit_sha256`, `ordinary_path`, and `ordinary_sha256` for the two evaluator-written canonical request files below. `candidate_check_attempts` starts empty and contains the two immutable routing-probe lifecycles after they are prepared/finalized. `candidate_check_evidence_path` and `candidate_check_evidence_sha256` are null after `prepare` and become the exact run-relative `candidate-checks/evidence.json` path and reopened raw-byte hash only through successful `record-candidate-checks`; scoring requires both non-null. `prepare` strict-resolves the requested empty `--run-dir` and exact fixture directory, freezes them as canonical absolute `run_root` and `fixture_root`, computes `fixture_tree_sha256` with `TREE_SHA256_V1`, and writes the state only at `<run_root>/prepared-run.json`; every later evaluator command requires the same roots, state path, and fixture tree bytes. Every one of the 13 matrix records has exactly `run_id`, `case_id`, `arm`, `role`, `phase`, `execution_kind`, `consumes_run_id`, `resume_of_run_id`, `controller_lineage_id`, `controller_state_path`, `controller_state_sha256`, `resumed_from_state_sha256`, `terminal_controller_state_path`, `terminal_controller_state_sha256`, `input_envelope_path`, `input_envelope_sha256`, `outer_attempt_ids`, `attempt`, `runtime_agent_id`, `output_path`, `output_sha256`, `plan_snapshot_path`, `plan_snapshot_sha256`, `package_snapshot_path`, `package_snapshot_tree_sha256`, `consulted_sources_path`, `consulted_sources_sha256`, `agent_runs_path`, `agent_runs_sha256`, `slot_ledger_path`, `slot_ledger_sha256`, `started_at_utc`, `ended_at_utc`, and `status`. Enums are `arm=legacy|v2`, `role=planner|implementer`, `phase=initial|resumed`, `execution_kind=SINGLE_AGENT|PARENT_ORCHESTRATED_V2|EVALUATOR_DERIVED_NO_PLAN`, and `status=WAITING_ON_INITIALIZATION|WAITING_ON_DEPENDENCY|WAITING_ON_RESUME|BLOCKED_READY_TO_RECORD|PREPARED|RECORDED`. Candidate initial planner rows start `WAITING_ON_INITIALIZATION` with fixed input path/hash, `controller_lineage_id=run_id`, and null preparation/terminal controller snapshots and start fields; legacy initial planners start `PREPARED` with null lineage and controller fields. Implementer rows start `WAITING_ON_DEPENDENCY`, `execution_kind=SINGLE_AGENT`, and null lineage/controller fields. Only `record-no-plan` may atomically change a waiting legacy implementer to `EVALUATOR_DERIVED_NO_PLAN` when its exact producer is recorded `BLOCKED`; no prepared or attempted row may change execution kind. The resumed V2 planner starts `WAITING_ON_RESUME` with `controller_lineage_id=resume_of_run_id`. `outer_attempt_ids` starts empty; attempt, runtime/output/terminal-snapshot/plan/package/consulted-source/agent-runs/slot-ledger/end fields are null before recording. Before creating any matrix row, `prepare` revalidates the complete authority and independent review, copies both exact files into run-owned immutable storage, reopens them, stores their relative paths/hashes, and derives every case request, visible input, public contract, implementation root, and hidden-gold file from that authority. A weakened, substituted, unreviewed, post-review-edited, or untraceable value blocks preparation before any candidate or legacy agent runs.

Evaluator storage is rooted once. Root-owned files are `<run_root>/prepared-run.json`, `recorded-matrix.json`, `evaluation-evidence.json`, and `score.json`. Candidate-check storage is exactly `<run_root>/candidate-checks/requests/explicit.json`, `requests/ordinary.json`, `attempts/<attempt-id>/input.json`, `output.json`, `released-slot.json`, and `token.json`, plus `explicit-routing.json`, `ordinary-routing.json`, `slot-ledger.json`, `managed-before.json`, `managed-after.json`, and `evidence.json`. Every logical row owns `<run_root>/rows/<run-id>/`; its fixed locations are `input.json`, preparation snapshot `controller-state.json`, `resume-source.json`, `attempts/<attempt-id>/input.json`, `attempts/<attempt-id>/output.json`, `record/transaction.json`, `record/staging/`, content-addressed terminal snapshots `recorded/controller-state/<sha256>.json`, `recorded/output.json`, `recorded/plan.md`, `recorded/package/`, `consulted-sources.json`, `agent-runs.json`, `slot-ledger.json`, and `boundary-trace.json`. Every candidate initial planner owns one live controller lineage at `<run_root>/controller-lineages/<initial-run-id>/task/`, whose immutable state path is `task/.plan-playbook-v2/state.json`; its one resumed row reuses that lineage ID and path. Initialization transactions alone live at `<run_root>/initialization/<run-id>/transaction.json`; record publication uses only the row-owned record transaction below. Every matrix, outer-attempt, or candidate-check path is a normalized run-root-relative POSIX path. `controller_state_path` always names the immutable preparation snapshot created by initialize/resume; `terminal_controller_state_path` names only the content-addressed snapshot committed by `record`; the mutable live path is derived only from `controller_lineage_id`. Evaluator reopening strict-resolves beneath `run_root`, rejects absolute paths, traversal, symlinks, changed roots, and every cross-row path except the resumed row's exact `resume_of_run_id` controller lineage. It re-hashes bytes or trees before use. External fixture, repository, and research-package roots remain separately frozen absolute authorities and are never stored as evaluator-owned relative paths.

`prepare` writes two canonical routing requests before prepared-run. Each has exactly `schema_version`, `probe`, `invocation`, `request`, and `output_contract`; `output_contract=ROUTING_PROBE_V1`, both requests use the same non-empty ordinary planning request that names no expected skill or verdict, `CANDIDATE_EXPLICIT` has `invocation=$plan-playbook-v2`, and `ORDINARY_LEGACY` has null invocation. `prepare-routing-probe` accepts each probe exactly once, reopens its prepared request, requires a matching reserved shared slot, allocates a globally unique attempt/runtime lifecycle, writes the immutable input and token, and appends PREPARED to `candidate_check_attempts`. `finalize-routing-probe` uses the same status, identity, output, released-slot projection/digest, retry, and exact-replay rules as ordinary evaluator attempts. A successful raw agent output has exactly `schema_version`, `input_sha256`, `invocation`, `selected_skill`, and `completed_at_utc`; it must bind the immutable request and invocation, but it cannot assert an expected skill, tree hash, or pass result.

Each evaluator-derived routing result has exactly `schema_version`, `probe`, `attempt_id`, `runtime_agent_id`, `slot_id`, `request_sha256`, `output_path`, `output_sha256`, `released_slot_path`, `released_slot_sha256`, `invocation`, `selected_skill`, `selected_tree_sha256`, `expected_skill`, `passed`, and `recorded_at_utc`. `record-candidate-checks` accepts only the two finalized SUCCEEDED routing-probe tokens and their authoritative shared slot ledger; it reopens each prepared request, raw output, attempt, and released-slot projection, rejects reused runtime or slot identity, and derives the selected tree itself by reopening and hashing the selected skill's content-addressed backup in the managed-after snapshot. The candidate probe requires selected and expected skill `plan-playbook-v2` and the prepared candidate tree; the ordinary probe requires selected and expected skill `plan-playbook` and the prepared legacy tree. `passed` is evaluator-derived and cannot be supplied by an agent or caller.

`record-candidate-checks` snapshots those derived routing results, the authoritative slot ledger, and the exact section-8.3 managed-before and managed-after snapshots into the fixed candidate-check paths. For every PRESENT managed skill in both snapshots it strict-resolves `<backup_root>/<backup_relpath>`, rejects symlinks, recomputes `TREE_SHA256_V1`, and requires equality with that skill's recorded tree hash; ABSENT records require null backup paths and no backup tree. It then derives all three booleans with the evaluator routing function and `compare-managed` using exactly `allow-added=plan-playbook-v2` and `allow-changed=_shared,research-playbook`, and atomically writes `candidate-checks/evidence.json` with exactly `schema_version`, `explicit_routing_path`, `explicit_routing_sha256`, `ordinary_routing_path`, `ordinary_routing_sha256`, `slot_ledger_path`, `slot_ledger_sha256`, `managed_before_path`, `managed_before_sha256`, `managed_after_path`, `managed_after_sha256`, `candidate_explicit_routing`, `ordinary_legacy_routing`, `managed_projection_clean`, and `recorded_at_utc`. It reopens that file and atomically binds its relative path/hash into prepared-run. All five paths are fixed candidate-check-relative paths, every boolean is derived rather than trusted, and all timestamps are canonical UTC. Exact byte-identical replay returns the original result; changed attempt/request/output/slot/backup bytes, a second recording with different input, a probe/tree mismatch, or a managed-snapshot comparison failure returns nonzero without rebinding prepared-run.

`initialize-planner` is the sole owner of candidate initial controller creation and uses `<run_root>/initialization/<run-id>/transaction.json`. Before `init`, it writes/fsyncs exact intent `{schema_version, state=INTENT, run_id, predecessor_prepared_run_sha256, input_envelope_sha256, controller_lineage_id, controller_live_state_path, controller_state_path, created_at_utc}`. `controller_lineage_id` equals the initial run ID, the live path is the derived lineage state, and `controller_state_path` is that row's immutable snapshot path. It invokes candidate `init` with `--task-directory <run_root>/controller-lineages/<run-id>/task/` only when the live state path is absent. After validating the published live controller bytes, it atomically copies and re-hashes them into the row snapshot, computes the exact successor prepared-run bytes, and replaces the receipt with exact completed form `{schema_version, state=COMPLETED, run_id, predecessor_prepared_run_sha256, input_envelope_sha256, controller_lineage_id, controller_live_state_path, controller_state_path, controller_state_sha256, target_row_status, started_at_utc, result}`, where target status is `PREPARED|BLOCKED_READY_TO_RECORD`. `result` is exactly `{schema_version, command, ok, run_id, status, controller_state_path, controller_state_sha256, prepared_run_sha256, code}` with `command=initialize-planner`, `ok=true`, `status` equal to the target row status, run-root-relative immutable snapshot path, hashes of the row snapshot and computed successor matrix, and `code=PLANNER_INITIALIZED|PLANNER_BLOCKED_READY_TO_RECORD` respectively. It then atomically publishes those exact successor prepared-run bytes.

A rejected `initialize-planner` emits the same nine fields with `ok=false`, the unchanged current row status, current prepared-run hash, controller path/hash null only when no valid controller exists, and one stable non-empty failure code; it does not write a COMPLETED receipt or alter the matrix. Successful first execution and every successful recovery/replay emit canonical JSON for the stored `result` object byte-for-byte; failure replay is derived from unchanged state and the same code. Human prose and a nested controller `init` envelope are never exposed as the evaluator command result.

Every entry recovers first: INTENT plus absent live controller state runs init; INTENT plus matching live state creates or validates the immutable row snapshot, computes the same successor, and completes the receipt without rerunning init; COMPLETED plus predecessor matrix applies the recorded successor bytes; COMPLETED plus the exact successor row returns the stored result; any other lineage, state, snapshot, input, path, hash, or row conflicts. Tests inject crashes after intent, live controller publication, row snapshot publication, completed receipt, and matrix publication for sufficient and blocked rows and assert byte-identical successful stdout before and after recovery.

Every `outer_attempts` record has exactly `attempt_id`, `attempt_sequence`, `run_id`, `role`, `input_envelope_path`, `input_envelope_sha256`, `slot_id`, `status`, `runtime_agent_id`, `output_path`, `output_sha256`, `prepared_at_utc`, and `finalized_at_utc`. Status and nullability use the exact evaluator `agent-runs.json` terminal rules below plus `PREPARED`, whose runtime/output/finalized fields are null. `prepare-attempt` accepts only a PREPARED logical row, reopens its fixed input bytes, requires a matching reserved slot, assigns the next global monotonic sequence, atomically appends PREPARED, appends its ID to that row, and emits a hash-bound token. `finalize-attempt` requires that unchanged token and exact status-appropriate released slot evidence, snapshots any allowed output under the attempt root, and atomically finalizes once. One retry is allowed only after terminal non-success. Exact replay is idempotent; conflicting token, hash, identity, order, or second finalization fails closed.

Every `candidate_check_attempts` record has exactly `attempt_id`, `attempt_sequence`, `probe`, `input_path`, `input_sha256`, `slot_id`, `status`, `runtime_agent_id`, `output_path`, `output_sha256`, `released_slot_path`, `released_slot_sha256`, `prepared_at_utc`, and `finalized_at_utc`. Sequence shares the evaluator's global monotonic attempt namespace; probe is one of the two candidate-check enums and each probe may have at most one SUCCEEDED attempt. Status/nullability, runtime uniqueness across row and routing attempts, released-slot derivation, retry allowance, and token replay use the exact outer-attempt rules. PREPARED has null runtime/output/released/finalized fields; every terminal status has non-null released-slot path/hash, and SUCCEEDED additionally requires runtime/output path/hash. `record-candidate-checks` rejects a missing success, a second success for one probe, or any agent/slot identity reused anywhere in the run.

Both evaluator-derived zero-agent shapes use one exact slot-ledger constant, `EVALUATOR_ZERO_AGENT_LEDGER_V1`. Its logical object is exactly `{version:2,max:1,slots:[]}` and its canonical UTF-8 bytes are exactly `{"max":1,"slots":[],"version":2}` with no trailing newline. The evaluator writes those bytes without calling mutable slot initialization, stores their SHA-256 in the row and transaction, and reopens byte-for-byte during record recovery, replay, scoring, and promotion evidence checks. `max=1` is the live helper's default capacity and is fixed here solely to make the no-agent artifact identity deterministic; any other key, order after canonicalization, value, slot entry, or byte sequence fails closed.

`record` accepts no caller output path. For `SINGLE_AGENT`, it requires a successful attempt token, reopens only that finalized evaluator-owned attempt snapshot, validates its role output and referenced plan under the per-attempt source policy, and uses those bytes as the logical output. For `PARENT_ORCHESTRATED_V2`, it never treats the draft producer or preparation snapshot as the logical planner result: it validates the preparation snapshot only as the lineage predecessor, strict-derives the live state path from `controller_lineage_id`, requires all outer and inner slots released and the live state terminal as `EMITTED` for PASS or the exact permitted `BLOCKED` result, snapshots those exact live bytes content-addressed, and derives the section-8.4 candidate envelope only from that terminal snapshot. A passing package must come from the derived controller-lineage task root, match the terminal snapshot's revision/plan hash, and pass canonical `validate-package`. The zero-agent initial research row captures the same terminal blocked bytes, which may equal its preparation bytes but remain separately bound as the record-time terminal identity, and forbids an attempt token. Raw draft/hardening outputs remain confined to their attempts. Every mode rejects symlinks, unrelated lineages, unapproved sibling rows, unfrozen roots, nonterminal live state, or caller-authored logical output.

Record publication is one row-owned transaction and the matrix transition is its commit point. `record` or `record-no-plan` first recovers `<row-root>/record/transaction.json`, then stages the terminal controller snapshot when applicable, derived logical output, plan/package snapshots when applicable, consulted sources, agent runs, slot ledger, and exact successor `prepared-run.json` bytes without changing the live matrix. The journal has exactly `{schema_version,transaction_id,state,run_id,predecessor_prepared_run_sha256,terminal_controller_state_sha256,output_sha256,plan_sha256,package_tree_sha256,consulted_sources_sha256,agent_runs_sha256,slot_ledger_sha256,successor_prepared_run_sha256,created_at_utc}`; nullable fields follow the row contract, and state is `PREPARED|ARTIFACTS_INSTALLED|MATRIX_PUBLISHED`. The transaction ID hashes the run ID, predecessor matrix hash, terminal state hash, all staged result hashes, and successor matrix hash. After fsyncing staging, the command writes/fsyncs `PREPARED`, installs and reopens every row-owned artifact including `recorded/controller-state/<terminal-sha256>.json` when applicable, sets `ARTIFACTS_INSTALLED`, re-hashes any live controller state and requires it still equals the terminal snapshot, then atomically publishes the successor prepared-run bytes last and sets `MATRIX_PUBLISHED`. Only that successor matrix stores the final paths/hashes, actual execution kind, and `RECORDED` status.

Recovery from `PREPARED|ARTIFACTS_INSTALLED` validates the predecessor matrix, staged/installed hashes, and unchanged terminal live-state hash, then completes the same artifact installation and matrix publication; changed live state or conflicting bytes fails closed with the predecessor matrix unchanged. If the successor matrix hash is already present after a crash, recovery treats the matrix as published only after every recorded artifact and terminal snapshot reopens and matches, sets `MATRIX_PUBLISHED`, and cleans staging/journal. `MATRIX_PUBLISHED` verifies and cleans only. Exact replay from the matching `RECORDED` row reopens every bound byte/tree and returns the stored result; another predecessor, terminal state, output, package, lifecycle file, transaction, or successor hash conflicts. Tests interrupt after staging, PREPARED, each artifact class, ARTIFACTS_INSTALLED, live-state recheck, matrix publication, and MATRIX_PUBLISHED for sufficient, blocked, and resumed V2 rows.

`materialize-input` accepts only a waiting implementer row whose producer is `RECORDED` with `terminal_verdict=PASS` and a non-null plan snapshot. It reopens only the producer's run-owned output and plan/package snapshots, validates every stored hash, writes the exact implementer input envelope from those snapshots, computes the envelope hash from bytes, and atomically changes only that row to `PREPARED`. It is idempotent for the same producer snapshot hashes and rejects a blocked or changed producer, a second materialization with different bytes, or execution of a waiting row.

`record-no-plan` accepts only a `WAITING_ON_DEPENDENCY` legacy implementer row with no attempts or input envelope whose exact `consumes_run_id` producer is `RECORDED`, `arm=legacy`, and validly `terminal_verdict=BLOCKED` with null plan/package snapshots. It reopens that producer's immutable output, copies its non-empty clarification and unresolved-choice diagnostics, and derives the section-8.4 no-plan implementer envelope with null plan hash, `can_implement=false`, reason `NO_PLAN_FROM_BLOCKED_PLANNER`, empty actions and source lists, and no hidden IDs. It derives empty canonical consulted-sources and agent-runs files plus the exact `EVALUATOR_ZERO_AGENT_LEDGER_V1` bytes; sets attempt zero, runtime null, and both row timestamps to the producer's frozen end timestamp; changes execution kind to `EVALUATOR_DERIVED_NO_PLAN`; and publishes through the same artifact-first, matrix-last row transaction. Exact replay returns the stored result; any producer PASS/change, prior input/attempt, caller output, nonempty lifecycle/source file, changed zero-agent-ledger byte, or conflicting transaction fails closed.

`materialize-resume` accepts only the evidence-uncertain V2 row in `WAITING_ON_RESUME`. It requires `controller_lineage_id=resume_of_run_id` and reopens the predecessor's immutable blocked-state snapshot. It never copies, relocates, or rebases controller state. On first entry, the derived live lineage state must equal that predecessor snapshot. On recovery, a valid controller resume receipt may instead bind the live state to its exact predecessor or successor hash: predecessor completes controller resume; successor skips reinvocation and continues row snapshot publication; any other hash fails closed. The evaluator validates the external package, writes the exact EVIDENCE resolution source at the resumed row's `resume-source.json`, and invokes controller `prepare-resume-bundle` and `resume` against the same live lineage state and its controller-owned deterministic resume directory. After successful resume, it atomically snapshots the successor live state into the resumed row's `controller-state.json`, stores that snapshot path/current hash plus the predecessor snapshot hash, bundle/tree/journal/receipt evidence, and changes the row to `PREPARED`. The predecessor row keeps its immutable blocked snapshot. ## 14. Failure, Resume, and Idempotency

- Controller writes are atomic and validate old state before replacement.
- Attempts are reserved and budgeted before spawn; repeating an exact prepare/finalize command is idempotent only when all IDs and hashes match; conflicting reuse fails closed.
- A malformed agent envelope is a failed attempt and never a PASS.
- An agent completion without close evidence is non-terminal.
- A plan edit without `record-revision` is state drift and blocks the next stage.
- A revision invalidates all earlier stage results, including unaffected-looking stages.
- A revision also clears implementation authorization; no consumer may resume until the successor package receives a newly bound receipt.
- A missing research route returns `BLOCKED`, not a guessed DIRECT plan.
- Package emission derives identity before staging, writes PREPARING before the first staging mutation, reuses its durable emitted timestamp during recovery, and recovers its existing-root journal before new work; a `MANIFEST_PUBLISHING` crash is decided from the durable expected manifest and complete-package validation, pre-publication failure restores prior owned files, and unrelated siblings are never touched.
- Evaluator authority review is completed and hash-bound before candidate execution; prepare is immutable and derives every scoring-relevant fixture byte from that independently reviewed source authority; record snapshots outputs into run-owned storage, validates bounded consulted sources and the real shared slot ledger for agent-backed rows, derives the exact ledger constant for zero-agent rows, and rejects changed authority, review, matrices, or hashes; dependency/resume materialization reads only snapshots and preserves controller lineage; routing checks require two evaluator-prepared, agent-executed, released-slot-bound attempts; `record-candidate-checks` snapshots those lifecycles, derives the routing results, and re-hashes every managed backup tree before binding the evidence; score writes a hash-bound evidence manifest and uses the same derivation function as read-only `validate-score`; promotion plan and verify re-run that validator over the frozen fixture, every row authority, routing lifecycles, and managed backup bytes instead of trusting score booleans or snapshot JSON alone.
- Promotion plan is immutable; apply rejects source, score, manifest, installed-root, or tracked-path drift.
- Every promotion command recovers the durable journal before work; uncertain transitional states roll back, stable handoff states revalidate, and any failed apply, validation, live, or verification stage must prove restored owned-path hashes before control returns. `COMMITTED` remains immutable and cannot be reopened: any defect found afterward blocks shipping and starts a fresh corrective candidate from the committed canonical baseline, reruns affected tests plus the complete practical evaluation and score validation, passes independent `verify-work`, creates a new non-overlapping promotion transaction, obtains fresh promotion approval, and repeats apply, validate, live, and verify before closeout.
