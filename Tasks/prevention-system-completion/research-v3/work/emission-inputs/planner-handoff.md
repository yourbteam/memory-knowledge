# Planner handoff: mechanical-error prevention system

## Planning objective

Produce one bounded implementation plan that closes the eight planner-owned gaps below against all 22 frozen obligations. Preserve the fixed acceptance baseline: zero raw JSON/text patching in governed runs, zero repeated mechanical-failure fingerprints, no under-budget long-unit start, mandatory reuse of a same-path-verified correction, at least 95% registered deterministic dispatch for recurring actions, and mechanical overhead at or below 10% with 5% reported as the desired target.

## Required implementation slices

1. **System-wide sequence entry points — GAP-ENTRYPOINT-SYSTEM-WIDE.** Give every registered operational sequence one executable owner adapter from validated initialization through terminal verification. Inventory all 25 registry rows and test composite/non-standalone rows through explicit owner adapters.
2. **Typed dispatch — GAP-TYPED-DISPATCH.** Replace governed request/context JSON files, JSON argv, command strings, arbitrary argv, free-text correction fields, and rendered registry parsing with closed typed operations and schema validation at their authoritative boundary.
3. **Authoritative interception — GAP-AUTHORITATIVE-INTERCEPTION.** Put selection before dispatch. Supported Bash, apply_patch, and MCP actions may use managed PreToolUse interception; every unsupported class must be structurally withheld, covered by an authoritative future host hook, or fail visibly before execution. Do not claim universal Codex-hook coverage.
4. **Mandatory correction replacement — GAP-MANDATORY-CORRECTION.** Persist a failed predecessor prohibition and make the same-path-verified successor the mandatory selector result. A repeated fingerprint must be rejected before dispatch.
5. **Joined causal learning — GAP-CAUSAL-LEARNING.** Persist and query one lineage from intent through attempted action, failure, diagnosis, corrected action, same-path verification, discovery, promotion, registered verification, and later mandatory reuse. Later reuse must be proved before dispatch, not recognized after execution.
6. **Full-unit budget admission — GAP-FULL-UNIT-ADMISSION.** Atomically reserve core work, all three lenses, adjudication, expected materialization, terminal emission, and bounded retries before any long role or external effect starts. Prove that one unit below the requirement launches zero long work.
7. **Common durable resume — GAP-COMMON-DURABLE-RESUME.** Introduce a common transition/effect identity, reconciliation rule, and branch/worktree/run ownership key across controllers. Verify crash recovery before and after every effect so reinvocation advances from the next valid transition without duplicating effects or consuming another run's state.
8. **System metrics — GAP-SYSTEM-METRICS.** Add canonical producers, denominators, windows, exclusions, and reproducible queries for registered use, raw dispatch, mechanical-failure time, repeated fingerprints, promoted-sequence reuse, prevented failures, and mechanical overhead.

## Accepted limitation

GAP-FINITE-EVIDENCE-COMPLETENESS remains explicit: inaccessible external automation internals were not inspected. Treat each through black-box initialization-to-terminal adapter acceptance; do not infer implementation details or mark the system complete without that evidence.

## Plan constraints

- Use the evidence and readiness anchors in this package; do not invent API, event, schema, or database names.
- Fix authoritative contracts instead of accumulating parser aliases or compatibility exceptions.
- Keep phase-ledger contracts unchanged unless separately approved.
- Separate current-runtime evidence from future implementation obligations.
- Map every plan step to requirement IDs, files/symbols, tests, emitted evidence, and a rollback or containment boundary where applicable.

## Completion evidence required from implementation

The final review must include event-backed negative tests for zero raw dispatch and zero repeated fingerprints, a pre-dispatch rejection test for a prohibited predecessor, a one-unit-below budget test with zero launched long work, crash/restart tests across branch and multiple-run identities, a representative governed corpus proving registered use is at least 95%, and an overhead report using `mechanical_seconds / governed_active_seconds` with separately classified exclusions and both 10% and 5% thresholds reported.
